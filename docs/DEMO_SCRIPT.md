# SoundSight — Demo Script

**Target: 5–7 minutes** | Rehearse twice with a timer.

---

## Setup (before the room fills)

1. `python scripts/seed_db.py --clear --days 14` — fresh two-week history
2. Start backend: `cd backend && uvicorn app.main:app --reload`
3. Start frontend: `cd frontend && npm run dev`
4. Open browser to `http://localhost:5173` — Live Dashboard visible
5. Have a second terminal ready with `python scripts/inject_event.py --help`
6. Plug in ESP32 (if available); verify it shows up in **Devices** page
7. Pre-load phone with audio clips: `doorbell.mp3`, `fire_alarm.mp3`,
   `glass_break.mp3`, `baby_crying.mp3`, `timer_beep.mp3`

---

## Flow (timed)

### 0:00 — Hook (30 s)

> "430 million people worldwide are deaf or hard of hearing.  
> In their own homes, a smoke alarm, a doorbell, a baby crying — can all go
> unnoticed. SoundSight changes that."

Walk to the device. Point at the ESP32 + mic + LED ring.

---

### 0:30 — Live detection demo (2 min)

**Option A — real hardware**
1. Ring the doorbell (phone → speaker, or a physical bell).
2. Point at the dashboard: a **blue doorbell card** appears in real time.
3. Show the LED ring flash blue on the ESP32.
4. Play fire alarm clip. Show red card + continuous LED + vibration motor.

**Option B — fallback injection** *(if hardware is flaky)*
```bash
python scripts/inject_event.py --class doorbell --device-id 1
python scripts/inject_event.py --class fire_alarm --device-id 1
```
The dashboard updates identically — same WebSocket path, same card.

> "The ESP32 captures audio, sends raw PCM to the backend, our ML classifier
> identifies the sound in real time, and the result is broadcast to every
> connected device — LED ring, phone, laptop."

---

### 2:30 — AI pipeline walkthrough (1 min 30 s)

Switch to the **History** page. Click a fire alarm event → show the LLM summary.

> "Every event gets a short natural-language explanation generated by a local
> Llama 3.1 model running through Ollama — no cloud, no API key, no data
> leaving the building."

Switch to **Rules**. Type into the NL text box:

> *"Vibrate urgently if glass breaks after 22:00"*

Hit submit. Show the structured rule that appears below.

> "LangChain parses that sentence into a typed rule with trigger, priority,
> time window — the model never hallucinates a field that doesn't exist."

---

### 4:00 — Reports & memory (1 min)

Switch to **Reports → Daily**.

> "Every morning the user gets a daily digest. The agent queries the last
> 24 hours through our MCP tools, retrieves relevant context from ChromaDB,
> and writes a calm, factual summary — no alarm fatigue."

Point out the baseline comparison in the text if an anomaly appears.

> "If a sound lasts three standard deviations longer than usual, the system
> flags it. That's the long-term memory layer — baselines computed nightly
> from 30 days of history."

---

### 5:00 — Onboarding (30 s, optional if time allows)

Switch to **Onboarding**. Type:

> *"I'm elderly and live alone. I care most about fire alarms and doorbells."*

Show the generated profile: enabled classes, priority, quiet hours.

> "The very first time a user opens the app, one sentence is enough to
> configure the whole alert system."

---

### 5:30 — Close (30 s)

> "SoundSight runs entirely offline — Ollama, ChromaDB, and the ML model
> are all local. Privacy by default, no subscription, and it works even
> when the internet is down."

> "We're Stefan and Samuel. Happy to take questions."

## Fallback points

| What breaks | What to show instead |
|---|---|
| ESP32 not connecting | `inject_event.py` — same WS path, same UI update |
| Ollama not running | LLM summary shown as `null`; all other features work |
| ChromaDB error | RAG silently skipped; event cards and reports still work |
| Frontend crashes | Show the API directly: `curl localhost:8000/api/events` |
| Everything fails | Walk through the architecture diagram on the slides |

---

## Q&A cheat sheet

| Question | Key point |
|---|---|
| Why Ollama instead of the Claude/OpenAI API? | Privacy, cost, works fully offline — critical for a home device |
| Why MCP? | Separates reasoning from data access; tools are reusable across agents |
| Why RAG? | Grounds the LLM in the user's actual event history, not just its training |
| Why local baselines not a chatbot? | Baselines are structured statistics, not conversation — wrong tool |
| Why FastAPI over Flask/Django? | Async-first, typed with Pydantic, WebSocket native, OpenAPI auto-docs |
| Why this ML class list? | Safety-first (fire, glass) + sufficient training data in ESC-50/UrbanSound8K |
| Why not TDOA for sound direction? | WiFi NTP jitter (~10 ms) is larger than the acoustic arrival window |
